What was built

Green City Tycoon is a browser-based sustainability management game. Players place buildings on a 9×9 island, earn money, grow a population, and balance air quality, happiness, renewable energy and resilience while preparing for climate disasters.

The play loop

  • Build income first, then fund cleaner infrastructure.
  • Wait two in-game days for construction to finish.
  • Organize events to unlock buildings and stack permanent multipliers.
  • Use adjacency synergies to reward thoughtful city layouts.
  • Answer four educational questions to reduce disaster damage.
  • Reach six demanding meter targets at the same time to win.

Why this stack fit

React + TypeScript kept a UI-heavy game organized and made large state objects safer to change. Zustand let the 3D scene and side panels share the same live city without prop chains. Three.js through React Three Fiber and Drei ultimately solved the visual limits of CSS pseudo-3D. Vite kept the feedback loop quick, while browser storage made a save system possible without a backend.

Human ↔ agent division

Marco set direction: the city-management premise, real-time pacing, random events, achievements, mobile priority, and repeated visual quality judgments. Screenshot critiques were especially important.

OpenCode executed: it proposed architecture, scaffolded and edited the code, implemented systems and models, diagnosed errors, ran builds, and iterated from feedback. The transcript also shows the agent sometimes declaring success too early—making human review essential.

What was difficult—and what worked unusually well

Costliest difficulty

CSS 3D became a visual dead end

Faces rendered as slivers, roofs floated, trees lay sideways and models spilled between tiles. Multiple confident fixes did not match the screenshots. Cost: at least eight recorded critique cycles and most of the first extended session.

Root cause: choosing CSS transforms for geometry that needed inspectable, camera-aware 3D primitives.

Systems difficulty

Balance changed as features compounded

Events multiply income, pollution, capacity and growth; disasters and adjacency then modify consequences. Several commits explicitly rebalance stats, happiness and population.

Root cause: adding interacting systems before a repeatable balance harness existed.

Engineering difficulty

Time and terrain edge cases

Speed changes once reset day progress; terrain blocks needed generation, clearing and entity identity fixes; mobile panels needed to pause without overriding manual pause.

Root cause: state transitions spread across animation timing, simulation ticks and UI behavior.

Wins worth repeating

One clock, many systems

A single accumulator-based animation loop drives timing without resetting progress when speed changes. Disaster effects mutate refs per frame to avoid React render churn.

Education affects play

The 110-question bank is meaningful because quiz performance reduces damage by 10–70%. Knowledge is a strategic resource rather than decoration.

Documentation stayed close

GAME_STATS.md records formulas, multipliers, disaster tables and objectives, making later balance work far easier to audit.

How to make the next build easier

Start with the technical risk, not the feature list. For this game, the risk was the city view. A one-building Three.js spike with four visible sides would have prevented most of the first session’s rework.

Skill recipe 01

Build a themed procedural building

Inputs: building purpose, footprint, palette, signature details, camera angles.

  1. Choose reusable Three.js primitives.
  2. Build the silhouette before decoration.
  3. Add recognizable details on all four sides.
  4. Render front, rear and both side views.
  5. Check scale and tile bounds, then register the model.

Output: one model component plus a four-angle review sheet.

Skill recipe 02

Add a complete disaster

Inputs: hazard, warning signs, level table, defenses, educational category.

  1. Add types and state phases.
  2. Define warning and damage formulas.
  3. Connect defenses and quiz reduction.
  4. Add low-cost 3D effects using refs.
  5. Test warning → quiz → active → recovery → report.

Output: a playable, documented disaster with a deterministic test path.

Skill recipe 03

Balance a simulation change

Inputs: current formulas, target early/mid/late milestones, sample city layouts.

  1. Write expected outcomes first.
  2. Run fixed-day scenarios.
  3. Compare progression bottlenecks.
  4. Change one multiplier family at a time.
  5. Update GAME_STATS.md with the same patch.

Output: tuned constants, before/after table and regression cases.

Skill recipe 04

Run a visual QA loop

Inputs: named scenes, desktop/mobile sizes, acceptance checklist.

  1. Launch a known saved state.
  2. Capture the same viewpoints each run.
  3. Compare spacing, clipping, contrast and labels.
  4. Patch one defect class.
  5. Re-capture before claiming completion.

Output: consistent screenshots and an evidence-backed pass/fail result.

What the day-one starter should contain

  • A React Three Fiber scene with orbit controls, lighting and a tile coordinate helper.
  • One reference building that proves four-sided decoration and correct scale.
  • A single accumulator game loop with pause, 1×, 2× and deterministic tick tests.
  • A typed Zustand store split into simulation, UI and persistence slices.
  • Seeded terrain generation so visual and balance tests reproduce the same map.
  • A scenario/debug panel for money, meters, events and disasters.
  • A formula table template linked to each balance constant.
  • Desktop and mobile screenshot checkpoints built into the definition of done.
