1. What was built

Green City Tycoon is a real-time city-management simulation on a 9×9 grid. Players place buildings that earn income, generate pollution, and shift the city's happiness, renewable energy, and resilience. The grid sits on a 3D scene with rotating camera, day-night lighting, and disaster animations. The core loop is a meter-driven trade-off puzzle: every building pulls some meters up and others down; the player's job is to balance them while surviving periodic natural disasters.

Core systems

  • 30 buildings across 7 categories (Economic, Green, Water, Energy, Coastal, Waste, Science), each with a hand-built 3D model. Six are starter; the rest unlock by completing in-game events.
  • 10 sequential events with multiplicative stat buffs and unique CSS illustration popups. Events are the primary progression: each one unlocks new buildings and stacks multiplies onto the previous ones.
  • 4 disaster types (tsunami, earthquake, drought, smog) that scale with event progress. Each has a 30% daily chance of a warning, an educational multiple-choice quiz (4 questions) that reduces damage up to 70%, and a 3-day recovery phase with a damage report.
  • 6 live meters: money, population, pollution, happiness, renewable energy, resilience. Happiness is a persistent accumulator at ×10 integer scale so it cannot drift through floating-point rounding.
  • 10 building adjacency synergies: pairs placed adjacent (N/S/E/W) give a per-day happiness bonus or penalty. Discovery triggers an advisory.
  • Terrain generation at game start: 1 mountain, 2 lakes, 4 forests, each with a clear cost and time.
  • 20 objectives that track player progress and surface next steps.
  • Tutorial, win/loss conditions, mobile-responsive layout, 2× speed control, pause.

What makes it distinctive

The game is built around an integer happiness meter with streak-driven penalties. Pollution above 50% or population above housing capacity starts a "streak" counter that grows the penalty day by day — a one-day pollution spike costs 0.5%, ten consecutive days cost 5%. This replaces the simpler flat-rate penalty approach used in most city builders and creates a real early-warning curve: players can ignore pollution for a few days without dying, but the meter suddenly accelerates downward once they let it go.

The adjacency system is also a teaching device. Putting a Park next to a House gives +0.2% happiness/day; putting a Factory next to a House costs −0.5% per day. The five positive pairs are weaker than the five negative pairs, so careless zoning punishes players more than thoughtful zoning rewards them.

  • App.tsx owns the only requestAnimationFrame loop. Time is accumulated (accRef += dt × gameSpeed) and a tick fires every 5 seconds (or 2.5s at 2× speed).
  • gameStore.ts (~900 lines) holds every state slice and the dispatch-style tick() action. It is the only place meters are computed. The store is deliberately kept fat to avoid prop drilling and re-render churn.
  • 3D components use direct useFrame + ref mutation for animations (tsunami walls, smog particles, earthquake wobble) so they do not trigger React re-renders.
  • Data files (buildings.ts, events.ts, questions.ts) are pure objects fed into the store. No fetches, no DB.
  • CSS for everything visual (1700+ lines in App.css). Building 3D models are entirely React-Three-Fiber primitive composition — no GLB, no FBX, no external assets.

Most-frequent workflows

The agent wrote the formula, wrote the code, ran the build, told the user what changed, and updated the doc. Skipping the doc was how drift started.
  2. Bug → minimal repro → diagnosis → fix → verify (recurred ~10 times). The "each frame = 1 day" bug is the canonical example. User reports symptom; agent reads the relevant useEffect; identifies the root cause; proposes a narrow fix; user confirms by reloading.
  3. Add new building → 3D model → map to category (recurred 3 times). For the 3 new water buildings added mid-project, the workflow was: write the data row, pick a shape, write a 30-50 line JSX model, wire it into the switch dispatch, build, verify with user.

  5. Doc sync (recurred ~15 times). Every change to a formula, building stat, or event got a companion edit to GAME_STATS.md. The agent treated this as part of the same change, not a separate task.

Asset generation

This project did not use any image-, audio-, or model-generation tools. Every visual asset is one of:

  • CSS-built UI (status bar, sidebars, buttons, meters, popups, modals, all 10 event illustrations, all meter bars, all warning toasts, all stat deltas).
  • React-Three-Fiber primitive composition for the 30 building 3D models. Each model is composed of Box, Cylinder, Sphere, Cone primitives positioned with args + position + rotation + material props. Average 30-50 lines per building, some up to 100.
  • CSS illustrations for the 10 event popups. Each is a 100-200 line CSS scene with named divs (e.g. .wr-sky, .wr-sea, .wr-tank) positioned absolutely on top of a gradient background.
  • One PNG asset at src/assets/hero.png (13 KB) — inherited from the project scaffold, not used in the gameplay UI.

The advantage of this approach: zero file-size concerns, fully responsive scalable visuals, no asset pipeline. The disadvantage: the 3D models are stylized rather than realistic. For this game — a meter-management puzzle — the stylized primitives read clearly and the meter-driven design choices dominate the gameplay loop.

4. Difficulties and what went well

What went wrong

① The CSS 3D "isometric" experiment was a dead end

Cost: ~10–15 hours of exploratory work producing buildings that rendered as thin slivers or floating parallelograms. The fundamental problem was that CSS transform: rotateX + rotateY with positioning absolute does not give you three orthogonal faces consistently across browsers and grid sizes.

Root cause: chose the rendering approach before exploring whether it would work. The video-game convention is to commit to a 2D "+ 2.5D extrapolated" approach OR full WebGL within the first day — CSS 3D is the worst of both worlds.

Resolution: Migrated to React Three Fiber. Deleted the CSS 3D code, wrote the 30 3D models from primitives. Initial 3D models were rough (no four-side decoration), then iterated.

② The "each frame = 1 day" timer bug

Cost: ~2 hours including debugging time and a day's gameplay wasted before the user noticed.

Root cause: The useEffect in App.tsx depended on tick, and when the Zustand selector returned a fresh-memoized wrapper, the effect re-mounted with lastTimeRef = 0. The first frame's dt was then timestamp - 0, a huge number, making the day-progress accumulator always exceed TICK_INTERVAL_MS and firing tick() every frame.

Resolution: Replaced the 0-sentinel with performance.now() initialization and added a Math.min(dt, 1000) clamp so any future timing glitch cannot snowball.

③ Pathological building balance iterations

Cost: Real play-test time and ~10 commits of `Balancing` style patches. The user kept saying "make this stronger" or "this is too weak" without precise numbers, leading to rounds of guess-and-test.

Root cause: Playtesting through a 5-second-per-day tick loop is slow. The user reported symptoms ("Factory makes me too much money") rather than tuned numerical targets.

Resolution: Developed a working formula vocabulary (e.g., "sticker happiness in ×10 integer scale, round each building to 1 decimal"). The user started giving feedback in the same vocabulary, which made iterations converge faster.

④ Stale BuildingModel3D.tsx dead code

Cost: Tricky edit calls because the file is ~1,600 lines and uses == pattern checks (e.g., id === 'transit_hub') referring to buildings that no longer exist in the data.

Resolution: Documented the rule in AGENTS.md: "never use write on BuildingModel3D.tsx — always use edit." Not fully cleaned up; the unused shape identifiers (charging_station, station) are still in the type union and 3D shape dispatch.

⑤ Git/migration context loss

The migrator from CSS 3D to React Three Fiber did not commit the old code first. ~10 hours of CSS 3D exploration exist only in the project's earlier Session Summary text file, not in the git history. Anyone reading this repo would assume the project started in React Three Fiber, which is misleading.

What went well

① The streak-based meter system

The "pollution above 50% → streak counter → escalating penalty" mechanic took about 3 iterations to land but became the most distinctive feature of the game. It encodes real-world feedback dynamics (people tolerate pollution briefly, then intolerance grows) without explicit modeling of psychological state.

② The educational minigame design

110 questions across 5 categories (15 tsunami + 15 earthquake + 15 drought + 15 smog + 50 general). The minigame genuinely works as a learning tool: score 4/4 → 70% damage reduction, which is enough to make disaster math feel like a strategy instead of a luck-of-the-draw. The teacher-character illi Heading feature on the intro screen turned dry Q&A into a framed scene.

③ Documentation as a by-product

Treating GAME_STATS.md as part of the change (not a follow-up task) kept formulas in sync with code. A user's "make happiness integer" request → agent wrote the formula, the code, the doc, and the build all in one pass. The user could review the formula against the actual code without reconciliation.

Reusable skills the next intern should have

Skill: "Tune a meter formula by 1.5×"

Inputs: a base rate (e.g., "0.1%/day happiness"), a target (e.g., "1.5× stronger, shown to 1 decimal").

Steps:

  1. Confirm the meter is at ×10 integer scale. If not, decide whether to scale up or to round the display output.
  2. Multiply the integer base rate by 1.5. If the result is non-integer, derivative-round to the nearest 0.1 in display, then convert back to an integer internal value.
  3. Update the data file (buildings.ts), the docs (GAME_STATS.md), and verify the formula in code matches the doc.
  4. Build and lint. Confirm zero new ts errors.

Output: one or more buildings with corrected happiness values, integer-stored, displayed to 1 decimal place, documented in GAME_STATS.md.

Skill: "Add a new building with a 3D model"

Inputs: an emoji, a name, a category, a cost, a stat block, an unlock event, and a desired 3D shape.

Steps:

  1. Add the definition to buildings.ts with all stat fields explicit (zero is fine, but no undefined).
  2. Pick a shape from the existing Shape union. If existing shapes don't fit, add a new shape string to the union and write a new SpecialShape3D component using Box / Cylinder / Sphere / Cone primitives.
  3. Add the case to the switch in BuildingModel3D.tsx's main component.
  4. Add the color to CATEGORY_COLORS if the category is new.
  5. Update GAME_STATS.md building tables.
  6. Build, lint, and have the user review the model in-game.

Output: a new playable building with a unique 3D model, dispatched correctly, balanced in the docs.

Skill: "Rebalance a meter with a streak-based penalty"

Inputs: trigger threshold (e.g., "pollution > 50"), linear coefficient (e.g., "1.0%/day at day 1"), escalation curve (e.g., "increase linearly with consecutive days").

Steps:

  1. Add a new state field like pollutionStreak to the Zustand store and the type definition.
  2. In the tick action, increment the streak if the trigger condition holds, reset to 0 if it doesn't.
  3. Compute the penalty as Math.min(cap, severity × streak). Severity is the relevant meter level (0–100). Streak is consecutive days.
  4. Cap the penalty at a sane max (e.g., 15%/day) so a runaway streak cannot drain the meter in one tick.
  5. Apply the penalty to the persistent meter (which is at ×10 integer scale).
  6. Document the formula in GAME_STATS.md with worked examples.

Output: a meter with a starter grace period followed by an escalating penalty that punishes neglect without a single-day death.

Skill: "Always-update-the-doc"

Inputs: any change to a formula, building stat, event, or game rule.

Steps:

  1. Make the code change.
  2. In the same response, update GAME_STATS.md to match the new values.
  3. Update AGENTS.md if the change introduces a new pattern or rule.
  4. Build and lint.

Output: the docs never drift from the code.

Starter template wishlist

  1. Render approach decided on day 1. The CSS 3D detour cost 10+ hours. A pre-pick from a dropdown (CSS 3D, 2.5D clip-path, Three.js, PixiJS) would have eliminated the detour.
  2. SVG art for the 30 buildings as a fallback, even if they eventually get replaced by 3D models. The intern could place them, get used to the game loop, and only swap to 3D once the rest of the game was working.
  3. Working rAF day loop with rollback, so the day-tick pattern is committed to in the first commit and not re-implemented three times.
  4. Pure-data building/event/question files with TypeScript discriminated unions and zero business logic. The intern should never write if (happensWhenThisCost) in the rendering code.
  5. A reusable "streak counter" pattern in the store, since penalties that escalate with time are a common pattern in real-time games.
  6. Documentation-in-repo from commit 1. The GAME_STATS.md was added in commit 4 of this project, but it should have been started in commit 1 so the formulas and the code would never drift apart.
  7. A "balance editor" dev panel with sliders for each formula coefficient, so the intern can tune values in real time without recompiling. Several iterations on this project's happiness/population formulas could have been 10-second slider drags instead of 30-second rebuild cycles.
  8. A bare-bones 3D grid with one demonstrative building, so the intern can see the rendering pipeline working before designing all 30 buildings.
